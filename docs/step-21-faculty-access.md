# Administrator-managed faculty access

Install `202610130006_faculty_access.sql` after the existing classroom/report/key-correction migrations. It seeds only the confirmed existing teacher account `cchakrapani@imthyderabad.edu.in` as administrator. Missing or unconfirmed bootstrap account aborts the whole migration. No other existing teacher is automatically approved. Changes are local until the frontend is published; the database restriction takes effect as soon as SQL is installed.

Admin > Faculty access allows a single email, pasted addresses, or CSV upload. Download template contains `email,name`; name is optional, and an email-only CSV also works. Uploads/pastes preview before approval, normalize case/outer spaces, reject duplicates or malformed rows, and support up to 500 addresses per batch. Approval imports are atomic and additive. They do not create Auth accounts, choose faculty passwords or send invitations. The administrator manages exact addresses, rather than allowing the entire college domain.

Approved faculty register through the existing teacher screen and confirm their own email. The approved list and administrator IDs live in private RLS-enabled tables. Admin RPCs require a verified, approved account with an administrator ID stored server-side. Client/user metadata cannot create administrator rights. Admins do not receive access to other teachers' quizzes or rosters. Administrator approvals cannot be removed through this screen.

Remove approval retains the allowlist record, accounts, quizzes and reports; it blocks existing tokens through current database approval checks and ends that teacher's active sessions. Restoration reopens the same saved workspace, while previously ended sessions stay ended. An in-flight email blocks removal until reviewed/finished; queued jobs cannot be claimed for a removed faculty owner. Removal and protected teacher operations serialize on approval/session locks. The UI rechecks access every 30 seconds and on focus. Existing downloads and information already seen cannot be recalled.

Signup is guarded transactionally by the profile trigger even without a dashboard hook, including rejecting anonymous Auth accounts. Student portal uses public token-protected room RPCs, not anonymous Auth accounts; it continues to work. Enable Authentication > Hooks > Before User Created using public.classpulse_before_user_created for a clear registration rejection. The hook is available on the Supabase Free tier. Browser roles cannot call it directly. Auth email changes must also use an approved address.

All current teacher-owned public tables receive an additional restrictive RLS policy. All current teacher SECURITY DEFINER RPCs receive classpulse_require_faculty() at function entry. Future migrations replacing these functions or adding tables must preserve/reapply the gate; keep the new privacy test current. Reapplying this migration is supported and tested.

Supabase Auth confirmation mail is separate from report delivery. Default Supabase SMTP restricts delivery to project-team addresses, so confirm/configure custom SMTP with the college provider before onboarding other faculty. Keep email confirmation enabled. SMTP setup is not activated in this step, and no real emails were sent.

Validation: isolated PostgreSQL tests cover admin spoofing, private list exposure, transactional CSV imports, active/removed/unconfirmed identities, hook permissions, trigger fallback, address-change bypass, direct-table and RPC revocation, email claim denial, session ending, restoration, student room entry and fixture rollback. Five CSV/list tests cover normalization, quotes, duplicates, malformed input and the 500-address limit. The real Admin component was tested in a local UI harness with fictional data; no connected Supabase approvals were changed during that UI test. Typecheck, production export and the full app regression suite passed. Actual project installation, enabling the hook and faculty signup/email delivery remain acceptance steps.
